# FF・厨房 月次実績レビュー

7店舗（上新田・朝日町・元町一・豊津中・青山台・白島二・原田南）のFFと店内厨房の実績を、前年の同じ月・同じ日付と比べるダッシュボードです。対象の月は、今年のCSVの日付から自動で決まります（3日以上データがある一番新しい月。11月のCSVを入れれば11月版になります）。

画面は7つのタブに分かれています。上の「FF／厨房」「店舗」「期間（累計・今週・先週・週ごと）」の切り替えは、すべてのタブに効きます。

| タブ | 内容 |
|---|---|
| 1 総合 | KPI 6枚（売上高・荒利益高・荒利益率・月末売上予測・廃棄率・販売率）＋補助KPI（販売数・廃棄高）、重要な変化・確認すべき店舗・異常値、優先アクション、**分析インサイト・改善提案**（ルールで自動作成） |
| 2 売上・荒利益 | 日別推移（前年＝薄い灰色・実績＝紺・予測＝ティールの点線。凡例クリックで表示切り替え）、月末着地予測と内訳（実績・残りの予測・予測の幅・参考予測）、**販売前年比と荒利前年比の推移（週別・月をまたいで表示）**、日別の荒利益高 前年同日比・荒利益率、先週比（差額・先週比（先週＝100%）・上がった／下がった単品）、カテゴリー別 |
| 3 廃棄 | 店舗別の廃棄高・廃棄率、日別廃棄高、カテゴリー別構成比、単品別 廃棄高ランキング |
| 4 単品別 生産判断 | 販売力×廃棄率の散布図、増産・維持・注意・減産・判定保留、カテゴリーと判定で絞り込み |
| 5 店舗別 | **店舗別 パフォーマンス比較**（並べ替えできる表・評価 🔴🟠🟢・指標を切り替えるランキンググラフと全店平均の線）、1店1日あたりのランキングと店舗平均との差、店舗×単品の増産・減産リスト |

| 7 アクション・教訓 | **改善アクション・教訓**（店舗名・課題・根拠となるKPI・推奨アクション・優先度 🔴🟠🟢・対応状況）、実施管理（推奨内容・担当・予定日・状況・実施日・実施後の実績）、改善候補（実績から自動抽出：廃棄削減・増産・急変）、前年同月の教訓 |

表は「表をコピー」（PowerPoint・Excel用）と「CSV」で書き出せます。グラフは「グラフをコピー」で高画質の画像になります。

## 見方

GitHub Pages のURLを開き、パスワードを入力すると表示されます。データはパスワードで暗号化してページに入れています。ただし、これはログインの代わりにはなりません（下の「セキュリティと公開範囲」）。

## データの更新方法

元のCSVには売上や担当者名が入っているため、GitHubには上げません（`data/` は `.gitignore` で除外しています）。更新は手元のパソコンで行います。

1. 新しいCSVを手元の `data/FF/`（FF）または `data/厨房/`（厨房）に入れます。
   - 店舗システムから出したCSV（Shift_JIS）をそのまま入れてください。
   - 同じ期間のファイルが重複しないようにしてください（古い「〜4まで」のファイルは、新しいファイルと入れ替えます）。
   - 前の月のCSV（今年・前年とも）は、消さずに残しておいてかまいません。月の集計には入らず、「販売前年比と荒利前年比の推移（週別）」のグラフで、その週まで線が伸びます。
2. パスワードを指定してレポートを作ります。

   ```bash
   pip install pandas numpy cryptography
   REPORT_PASSWORD=（パスワード） python scripts/build.py
   ```

   Windows（PowerShell）の場合：

   ```powershell
   $env:REPORT_PASSWORD="（パスワード）"; python scripts/build.py
   ```

3. できた `index.html` をGitHubに上げる（コミット・プッシュ）と、数分でGitHub Pagesに反映されます。

`REPORT_PASSWORD` を付けずに作った `index.html` は暗号化されていません。その場合はGitHubに上げないでください。

## 集計の決まり

- 前年比は同じ日付どうしで比べます（例：2026年11/1〜 と 2025年11/1〜）。
- 廃棄率＝廃棄数 ÷（販売数＋廃棄数）。マチカフェは売上・荒利益に含め、廃棄分析・単品の生産判断からは除きます。
- 減らす数の目安は、廃棄の約8割までにしています（廃棄ゼロの日もあり、同じ数を減らすと売り切れが出るため）。
- 期間は、今年のCSVに入っている最終日までで自動的に決まります（前年も同じ日付までで比べます）。
- 週別の前年比トレンドは、data/ にあるすべての週を出します（月曜始まり）。前年は同じ日付で、今年・前年の両方にデータがある店舗・日だけで比べます。その週に今年か前年のどちらかにしかないカテゴリーは、その週だけ外します。3日未満の週は出しません。
- FFは、からあげクン・マチカフェ・ホットFF・常温FF・サーマル常温・中華まん（什器販売）です。今年と前年の両方にあるカテゴリーだけを集計します。
- 店舗は `scripts/build.py` の `SN`（正式名→短い名前）に並んでいる店のうち、CSVに出てくる店です。新しい店を足すときは `SN` に1行足します。
- 天気の実績は、CSVの「天気・降水量・最高気温・最低気温・湿度」列（日ごとに全店同じ値）を使います（手入力は不要）。降水2mm以上を雨の日とします。
- 予報は吹田市（tenki.jp）の値を `data/forecast.json` に書きます：`{"issued":"11/9 12時発表","days":[[9,"雨時々曇",16,60], …]}`（日・天気・最高気温・降水確率%）。ファイルがなければ予報なしで作ります。
- 祝日は `scripts/build.py` の `HOLIDAYS` に年ごとに書きます（日曜・祝日として扱います）。
- 中華まんと気温の区分は、10月は22℃・26℃、ほかの月は前年のその月の最高気温を3等分して決めます。
- 先週比は、今週・先週のどちらかが3日未満（月初の端の週など）のときは出しません。

## 数字の決まり（追加分）

- 先週比は1日あたりで比べます（週によって日数が違うため）。前年比は前年の同じ日付どうしの比較です。
- 目標（予算）のデータはないため、目標比は表示しません。
- 月末着地予測＝実績＋残りの日（前年の同じ日 × 選んだ期間の前年比）。グラフでは点線、KPIでは別のカードで、実績と分けて表示します。
- データがない日（欠損）はグラフで空白、売上ゼロの日は0で表示します。比べる基準が0やない場合は「—」です。
- 販売日が3日未満の単品は「判定保留」とし、増産・減産の判定をしません。
- アクションの期待効果は上限の目安です。「直近の推移」は週ごとの実績で、施策の効果と断定するものではありません。

## セキュリティと公開範囲（GitHub Pages の限界）

- **このリポジトリは公開（public）です。** `index.html` は誰でもダウンロードできます。中のデータは AES-GCM（PBKDF2 100万回）で暗号化していますが、ファイルを手に入れた人は、手元で何度でもパスワードを試せます。
  - **短いパスワードや数字だけのパスワードは、時間をかければ破られます。** 英数字・記号を混ぜた12文字以上の長い合言葉にしてください。
  - パスワードを変えても、以前の `index.html`（Gitの履歴やダウンロード済みのファイル）は、古いパスワードで開けたままです。
- **パスワードは全員共通です。** 知っている人は全員、全店・全データを見られます。画面のデータを書き写したり、ブラウザから取り出したりすることも止められません。人ごと・店舗ごとの閲覧制限、ログイン、アクセス記録、退職者の締め出しはできません。
- **元データ（`data/`）はGitHubに上げません**（`.gitignore`）。暗号化せずに作った `index.html` も上げないでください。
- 売上・廃棄の数字を、社外秘として厳しく守る必要がある場合は、GitHub Pages ではなく、会社のアカウントでログインできる場所（Cloudflare Access・社内サーバー・Google Workspace の共有ドライブなど）に置くことをおすすめします。どこに置いてよいかは、社内規程（情報システム部門）を確認してください。

## 判定の基準（`template.html` の `CONFIG`）

画面の基準は `scripts/template.html` の `CONFIG` にまとめています。値は、もともと画面で使っていた基準と同じです。

| 名前 | 値 | 使う場所 |
|---|---|---|
| `wasteWarn` | 10（%） | 廃棄率の基準。総合KPIの「基準超」、インサイト、店舗の評価（🔴） |
| `wasteCaution` | 6（%） | 廃棄率の注意。総合KPI・店舗の評価（🟠） |
| `skuWasteLine` | 15（%） | 単品の廃棄率の線（散布図の赤い線・単品判定と同じ）。廃棄ランキングの強調 |
| `sellTarget` | なし | 販売率（数量）の目標。目標データがないため未設定。数字（例：90）を入れると、目標比とインサイトを出します |
| `marginGap` | 2（pt） | 店舗の荒利益率が全店より何pt低いと「注意」にするか |

- **荒利益率**＝荒利益高（廃棄控除後）÷ 販売高。
- **販売率（数量）**＝販売数 ÷（販売数＋廃棄数）。CSVに作成数がないため、販売数＋廃棄数を作成数の代わりに使います（＝100%−廃棄率）。金額ベースの販売率ではありません。マチカフェは除きます。
- **時間帯別の実績・生産計画**はCSVにないため、表示していません。

## 分析インサイト・改善提案（総合タブ）

ページの実績から、決まったルールで作ります（AIの文章生成やAPIは使いません）。各項目に「根拠（数字と基準）」と「推奨」を付けます。差や相関を示すもので、原因は断定しません。

| 区分 | 出す条件 |
|---|---|
| 売上 | 前年同期比（全店舗のデータがある同じ日付）が100%未満（🔴）／105%以上（🟢） |
| 荒利益 | 荒利益高の前年比と売上高の前年比の差が ±1pt 以上 |
| 廃棄 | 廃棄率が `wasteWarn` 以上（🔴）、前年より1pt以上の上昇（🟠）・低下（🟢） |
| 販売率 | `sellTarget` を設定したときだけ。目標未達（🟠） |
| カテゴリー | 売上の寄与度が −1pt 以下（🟠）、+2pt 以上（🟢） |
| 予測 | 月末着地予測が前年同月を下回る（🟠）・上回る（参考） |
| 店舗 | 店舗の評価が「要対策」「良好」（全店表示のとき） |
| 曜日 | 今月の曜日平均が、前年同月の同じ曜日平均の90%以下 |
| 先週比 | 1日あたりの売上が ±10%以上 |
| 単品 | 減産・増産の判定の件数 |

並び順は 要対策 → 注意 → 好調 → 参考、同じ区分の中は差の大きい順です。

## 店舗の評価と改善アクションの優先度

- 店舗の評価（店舗別 パフォーマンス比較）：🔴 要対策＝売上・荒利益の前年比がどちらも100%未満、または廃棄率 `wasteWarn` 以上。🟠 注意＝どちらか一方が100%未満、廃棄率 `wasteCaution` 以上、または荒利益率が全店より `marginGap` 以上低い。🟢 良好＝それ以外。
- 改善アクションの優先度：🔴 高＝確度「高」の改善候補（廃棄削減、売上・荒利の減少や廃棄の増加）と「要対策」の店舗。🟠 中＝確度「中」の同じ候補。🟢 好調＝増産の候補、良い方向の急変、「良好」の店舗。確度「低」と、試算で荒利益高が下がる候補は出しません。
- 対応状況は実施管理の記録です（保存のしかたは下の「実施管理」と同じ。この端末だけに一時保存し、共有は書き出し→管理者がまとめる）。

## 改善候補（自動抽出）の計算方法

`scripts/candidates.py` で、CSVの実績だけから店舗×単品・店舗×カテゴリーの候補を作ります。各候補には、対象期間、対象店舗、対象商品、データ件数（記録日数・CSV行数）、確度とその根拠、推奨アクション、試算を付けます。画面の「計算根拠を見る」では、**実績値**（CSVから計算した値）と**仮定値**（こちらで置いた前提）を分けて表示します。

### CSVから出す単価（実績値）

- **原価/個**＝(販売高−荒利益高)÷(販売数＋廃棄数)
  - 荒利益高は「販売高−作った分すべての原価」になっています。売れなかった日の荒利益高が −廃棄数×原価 になることで確かめました。
  - 同じ単品なら、日による差は0.1%程度です。
- **売価/個**＝販売高÷販売数（値引き後の平均）
- **廃棄高は定価ベース**です。廃棄を1個減らしたとき荒利益高が増えるのは、原価の分（廃棄高のおよそ半分）だけです。そのため「廃棄高の変化」と「荒利益高の変化」は別々に出します。

### 廃棄削減

過去の日別の実績に、「毎日 r 個少なく作る」を当てはめて計算します。

- 1日の荒利益高の変化＝ r×原価 − max(0, r−その日の廃棄数)×売価
- 期間の合計を7日分に直します（×7÷記録日数）。
- **r（仮定）**：廃棄の約8割まで（画面の「減らす数」と同じ決まり）。荒利益高が下がる場合は、2日に1回1個でも試します。それでも下がる単品は「減らさない」と表示します。
- **仮定**：来週も同じ日別の売れ方になる。廃棄ゼロの日は、作った分が全部売れていた。
- **確度**
  - 高：記録10日以上、かつ廃棄が出た日が50%以上
  - 中：記録5日以上、かつ廃棄が出た日が30%以上
  - 低：それ以外

### 増産

毎日1個多く作った場合を計算します。

- 廃棄が出た日：追加の1個は売れ残ります（−原価）。
- 廃棄ゼロの日：売り切れた時刻のデータがないため、需要がどこまであるかは分かりません。そこで「全部売れた場合」と「全部売れ残った場合」の両方を出し、損益分岐（原価÷売価以上が売れればプラス）も示します。
- 確度は最高でも「中」です。

### 急変

- **先週比**：日別の値で、ウェルチの t 値を使います。
- **前年比**：同じ日付どうしの差の t 値を使います。
- **確度**：|t|≥3 は高、≥2 は中、≥1.5 は低です。1.5未満の変化は出しません。
- 確度を1段階下げる場合：週の土日祝の日数が違うとき。
- 確度を「低」にする場合：前年から分類が変わったカテゴリー（2026年10月版のホットFF・常温FF。11月は前年の時点で既に移っていたため対象外）の前年比。
- 原因（天気・販促・欠品など）は、このデータからは特定できません。推奨アクションは「確認すること」として出します。

## 実施管理（アクションTAB）

詳しい設計は [docs/実施管理_設計.md](docs/実施管理_設計.md) にあります。

- **保存先**：ページ上での入力は、**その端末のブラウザにだけ**一時保存されます。他の人には見えず、ブラウザのデータを消すと消えます。
- **共有のしかた**：
  1. 各自が「書き出し（JSON）」をして、管理者に送ります。
  2. 管理者が、受け取ったファイルをまとめます。

     ```bash
     python scripts/merge_actions.py 受け取ったファイル1.json 受け取ったファイル2.json
     ```

     同じ記録は更新日時が新しい方を残し、2人が同じ記録を直していたら「競合」と表示します。まとめた結果は `data/actions.json` に書かれます。
  3. いつもどおりページを作り直して push します。共有版は暗号化してページに入り、全員に読み取り専用で表示されます。`data/` の中なので、GitHubには上げません。
- **実施後の実績**：実施日の前後で、同じ日数（最大7日）を1日あたりで比べ、CSVから自動計算します。
- **この仕組みでできないこと**：ログイン・本人確認、店舗ごとの権限、リアルタイムの共有、通知。これらにはバックエンドが必要です（設計書の5章）。

## 売上・荒利益タブ（SALES）の計算

- **前年同期比**：選んだ期間の中で、今年も前年も全店舗のデータがある同じ日付だけを使います（今年 ÷ 前年 − 1）。データのない日、一部の店舗しかない日、まだ来ていない日は、分子からも分母からも外します。前年の合計が0以下のときは前年比を出しません。
- **月末着地予測（簡易予測）**：着地＝1日〜最終日の実績＋残りの日の予測です。
  - 残りの日の予測＝前年の同じ日（最終日の翌日〜月末）の合計 × 前年比
  - 前年比は、上の「前年同期比」と同じ方法で出します。期間に週を選んだ場合は、その週の前年比を使います。
- **誤差の目安**：今年のデータで、途中の日（7日目〜最終日の3日前）までの前年比から残りを予測し、実績と比べた誤差の平均です。予測の範囲は「残りの予測 ×（1 ± 誤差の目安）」として表示します。
- **参考の予測**：今年の曜日区分（平日・土・日祝）ごとの1日平均で残りを埋めた値も並べて出します。2つの方法には差が出るので、どちらも簡易予測として扱ってください。
- **カテゴリーの寄与度**：寄与度＝カテゴリーの前年差 ÷ 前年の合計 ×100（pt）です。全カテゴリーを足すと、全体の前年比になります。
