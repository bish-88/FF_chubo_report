# 実施管理（アクションTAB）設計

改善候補から決めた施策について、推奨内容・実施担当・実施予定日・実施状況・実施後の実績を管理する仕組みの設計です。

## 1. 前提：いまの保存基盤

| 項目 | 現状 |
|---|---|
| 公開方式 | GitHub Pages（静的サイト）。サーバー側でプログラムは動かない |
| データ | CSVを手元で集計し、パスワード（全員共通の1つ）で暗号化してページに埋め込む |
| ログイン | なし。パスワードを知っている人は全員、同じ内容を見られる |
| 書き込み先 | なし。ページから GitHub やサーバーへ保存する仕組みはない |

このため、**ページ上で入力した内容を、全員で共有して永続保存することは今の仕組みではできません。** 画面でも「保存される」とは表示せず、保存先（この端末だけ／共有版）を常に表示します。

## 2. 管理する項目（データモデル）

1件＝1つの施策（店舗×商品）。

| 項目 | キー | 入力 | 説明 |
|---|---|---|---|
| ID | id | 自動 | `A20261020-xxxxx` |
| 候補キー | key | 自動 | 部門・店舗・商品・区分。元の改善候補とのひも付け |
| 部門・店舗・カテゴリー・商品・区分 | dept, store, cat, name, type | 自動 | 改善候補から写す |
| 推奨内容 | rec | 編集可 | 初期値は候補の推奨アクション |
| 登録時の根拠 | basis | 自動 | 登録した時点の対象期間・確度・試算（あとでデータが増えても変わらない） |
| 実施担当 | owner | 入力 | 個人名でなく役割（店長・夕勤リーダーなど）を推奨 |
| 実施予定日 | plan_date | 入力 | 予定日を過ぎても実施日が空なら「期限超過」 |
| 実施状況 | status | 選択 | 未着手／実施中／完了／見送り |
| 実施日 | done_date | 入力 | 実際に変えた日。実施後の実績の計算に使う |
| メモ・所感 | note | 入力 | 売り切れ時刻・現場の気づきなど |
| 実施後の実績 | （保存しない） | 自動 | CSVから毎回計算する（3章） |
| 作成日時・更新日時 | created_at, updated_at | 自動 | 更新日時は、まとめるときの新旧判定に使う |
| 更新者 | updated_by | — | 静的サイトでは本人確認ができないため、記録しない（5章） |

## 3. 実施後の実績（自動計算）

- 実施日の前と後で、**同じ日数（最大7日）**を1日あたりで比べる。
  - 例：実施日 10/12、データ 10/18 まで → 前 10/5〜11、後 10/12〜18。
- 指標は、販売数・廃棄数・荒利益高・廃棄高（定価ベース）。単品はCSVに記録のある日だけで平均し、記録のない日は欠損として扱う（0にしない）。
- 前後どちらかの記録が3日未満なら、「データ不足」と表示して比べない。
- 前後それぞれの土日祝の日数を表示する。天気・曜日・ほかの施策の影響も含むため、**差を施策の効果とは断定しない**。
- 実施日がデータの範囲外のとき、または実施後のデータがまだないときは、そのことを表示する。
- 計算はページ内（`actEval`）で行う。必要な日別データは、ビルド時に候補と共有版に出てくる 店舗×単品／店舗×カテゴリー の分だけ同梱する。
- 結果は、本物のCSVから別の方法で計算し直した値と一致することをテストで確認している（`tests/test_actions.py`）。

## 4. 静的サイト（GitHub Pages）で実現する範囲 ― 第1段階（実装済み）

### 仕組み

```
[各端末のブラウザ]                          [管理者のパソコン]                     [GitHub Pages]
 改善候補 →「実施管理に追加」                 data/actions.json（共有版の元）
 担当・予定日・状況・実施日を入力              ↑ scripts/merge_actions.py で
   ↓ 自動で一時保存（この端末だけ）              各自の書き出しファイルをまとめる
 「書き出し（JSON）」→ ファイルを管理者へ ──→  ↓ scripts/build.py（暗号化）  ──push──→  共有版を含むページ
                                                                                       （読み取り専用で全員に表示）
```

### できること

| 機能 | 方法 | 注意 |
|---|---|---|
| 候補から施策を登録 | 改善候補カードの「実施管理に追加」 | 登録済みの候補には状況を表示 |
| 担当・予定日・状況・実施日・メモの入力 | 表の中で直接編集 | — |
| 端末内の一時保存 | ブラウザの localStorage | **この端末・このブラウザだけ**。他の人には見えない。ブラウザのデータ削除・プライベートモードで消える。使えないブラウザでは「保存されない」と表示する |
| 共有 | 書き出し（JSON）→ 管理者が `merge_actions.py` でまとめる → ページを作り直す | 反映は管理者がページを作り直したとき。リアルタイムではない |
| 共有版の表示 | ページに暗号化して同梱。読み取り専用 | 直すと「この端末で変更」になり、また書き出しが必要 |
| 新旧の判定 | 更新日時が新しい方を残す。同じ記録を2人が直したら、まとめるときに「競合」と表示 | 古い方の変更は失われる |
| 期限超過の表示 | 予定日を過ぎても実施日が空 | 判定は閲覧している端末の日付 |
| 実施後の実績 | 3章のとおり自動計算 | データ更新（CSVの追加）で自動的に延びる |
| CSV出力 | 表示中の記録をCSVで書き出し | Excelで開ける（BOM付きUTF-8） |

### 運用手順（週1回の例）

1. 各店（または担当SV）：ページで記録を更新し、「書き出し（JSON）」をして管理者に送る。
2. 管理者：`python scripts/merge_actions.py 受け取ったファイル...` を実行し、`data/actions.json` を更新する。
3. 管理者：いつもどおり `REPORT_PASSWORD=… python scripts/build.py` → `index.html` をpushする。
4. 全員：ページを開き直すと、共有版に反映されている。端末内の古い変更は「共有版が新しい」と表示される。

`data/actions.json` は `data/` の中にあるため、GitHubには上げない（`.gitignore`）。ページには暗号化して入るので、見られるのはパスワードを知っている人だけ。このファイルの控えは、管理者が手元で保管する。

### 静的サイトでは**できないこと**

- 入力した内容を、その場で全員に共有すること
- 誰が入力・変更したかの確認（本人確認がないため、更新者は記録しない）
- 人や店舗ごとに、見られる範囲・直せる範囲を分けること（パスワードは全員共通）
- 期限の通知（メール・LINEなど）
- 写真の添付

## 5. バックエンド（認証・権限管理つきのサーバー）が必要な機能

| 機能 | 必要な理由 |
|---|---|
| 入力したらすぐ全員に共有・永続保存 | ブラウザの外に書き込み先（データベース）が要る |
| 個人ごとのログイン | 「誰が」を確かめるには本人確認が要る。共通パスワードでは区別できない |
| 権限管理（例：店長は自店だけ編集、SV・エリアは全店） | サーバー側でログインした人を確かめて、書き込みを断る仕組みが要る。ページ内のチェックだけでは迂回できる |
| 変更履歴（誰が・いつ・何を） | ログインした本人と時刻をサーバー側で記録する |
| アカウントの停止・退職者の締め出し | 共通パスワードでは全員のパスワードを変えるしかない |
| 期限の通知・リマインド | 決まった時刻にサーバー側でプログラムを動かす必要がある |
| 写真の添付 | ファイルの保存先が要る |
| CSV取り込みの自動化（毎日の自動更新） | 店舗システムからの自動連携は、社内システム側の対応も必要 |

### 選択肢の比較（どれも社内規程の確認が前提）

店舗の売上・廃棄データは社外秘にあたる可能性が高いため、**どのサービスにデータを置いてよいかは、会社（情報システム部門）の判断が必要**です。

| 方式 | ログイン | 権限 | 手軽さ | 注意 |
|---|---|---|---|---|
| A. claude.ai のアーティファクトの共有データベース（`db`・`user` 機能） | claude.ai のアカウント（オーナーと同じ組織のメンバー、または招待したゲスト） | データの場所ごとに「全員読める・本人だけ書ける」などのルール | 高い。いまのアーティファクト版にそのまま足せる | 使う人全員に claude.ai のアカウントが必要。GitHub Pages 版では使えない |
| B. Google スプレッドシート ＋ Apps Script | Google アカウント | シートの共有設定・保護範囲 | 高い。会社が Google Workspace なら導入しやすい | 細かい権限（自店だけ）は作り込みが必要 |
| C. Supabase など（データベース＋ログイン＋行ごとの権限） | メール・SSO など | 行ごとのアクセス制御（店舗ごと） | 中。GitHub Pages のページから直接使える | 外部サービスに保存するため、契約・規程の確認が必要 |
| D. Cloudflare Workers ＋ D1 ＋ Access など | 会社のアカウント（SSO）で入口を制限 | サーバー側で自由に作れる | 低い（開発が必要） | 運用・保守の担当が必要 |

## 6. おすすめの進め方

1. **いま（第1段階・実装済み）**：静的サイト版で運用を始める。項目・状況の区分・週1回の共有の流れが現場に合うかを確かめる。
2. **次（第2段階）**：使う人の数と社内規程を確認して、5章のA〜Dから選ぶ。
   - 使う人が数人で全員 claude.ai を使えるなら A
   - 会社が Google Workspace なら B
   - 店長全員が使い、店舗ごとの権限が必要なら C または D
3. データモデル（2章）は第2段階でもそのまま使える。書き出しファイル（JSON）は、そのまま移行元として使える。

## 7. 決めてもらう必要があること

- 実施管理を使う人（エリア担当だけか、店長・リーダーもか）
- 店舗の売上・廃棄データと実施記録を、どのサービスに置いてよいか（社内規程）
- 担当欄に個人名を入れてよいか（入れない場合は役割名で運用）
- 共有の頻度（週1回で足りるか、即時が必要か）
